## Interpretation

- **ผลเป็นลบ: V6 แพ้ V4 ทุก fold และแพ้เท่ากันทุก fold** (−0.00117 / −0.00116 / −0.00117, OOF 0.7906 vs 0.7918) ความต่างสม่ำเสมอขนาดนี้ไม่ใช่ noise จึงหยุดตามกฎ time budget: ไม่ refit, ไม่สร้างไฟล์ Kaggle, champion ยังเป็น V4 และไฟล์ส่งยังเป็น V4 refit (public LB 0.80371)
- **สาเหตุหลัก: LightGBM เป็น amount model ที่อ่อนกว่า CatBoost ชัดเจน** บนแถว spender คอลัมน์ α=0.5 ได้ 0.8462 vs CatBoost 0.8541 (−0.0079) และ LightGBM alone (w=0) แพ้ V4 −0.0059 การเฉลี่ยสองโมเดลจะได้กำไรเมื่อความแม่นใกล้กันและผิดคนละแบบ แต่ที่นี่ blend (0.8526) อยู่ระหว่างสองโมเดลและต่ำกว่า CatBoost จึงไม่มี "diversity bonus" มากพอจะชดเชยช่องว่างความแม่น
- **แม้เลือก w บน OOF เองก็ไม่ได้อะไร** OOF เพิ่มขึ้นทางเดียวจาก w=0 (0.7859) ถึง w=0.8 แล้วแบนที่ 0.7918 ถึง w=1.0; w ที่ดีที่สุด 0.9 ได้ +0.00012 / −0.00000 / +0.00001 เทียบ V4 คือเท่ากับ V4 แม้จะเป็นตัวเลขที่มองโลกในแง่ดีอยู่แล้ว แปลว่า LightGBM ไม่มีข้อมูลที่ CatBoost ยังไม่มี
- **แยกตาม bucket:** V6 แย่ลงที่ bucket 0 (+0.56M, +0.6%) และ >20k (+1.63M, +0.9%) ดีขึ้นเล็กน้อยที่ 1k-20k (−0.15M) และ >0-1k (−0.01M) error ของ bucket 0 มาจากแถวที่ p > 0.5 แต่ y = 0 ซึ่งได้ยอดจาก quantile ต่ำ (q ใกล้ 0.05)
- **Coverage อธิบาย bucket 0:** coverage > alpha แปลว่า quantile ที่ทำนายสูงเกินไป LightGBM สูงเกินทุก alpha (0.094 ที่ α=0.05 ถึง 0.535 ที่ α=0.5) ส่วน CatBoost สูงเกินที่ alpha ต่ำ (0.075 ที่ 0.05) และต่ำนิดหน่อยที่ 0.5 (0.489) blend จึงดัน quantile ต่ำให้สูงขึ้นอีก (0.082 ที่ 0.05) ยอดของ spender ที่ไม่แน่ใจจึงสูงขึ้น ซึ่งสอดคล้องกับ bucket 0 ที่แย่ลง (เป็นการอนุมานจากสองตาราง ไม่ได้แยกวัดตรง ๆ) ส่วนที่ α=0.5 blend ได้ coverage 0.503 ใกล้ 0.5 กว่า CatBoost แต่คะแนนกลับแย่กว่า: calibration ดีไม่ได้แปลว่า error ต่อแถวต่ำ
- **Crossing:** LightGBM แยก 10 โมเดลต่อ alpha จึงไขว้กัน 95.5% ของแถว (CatBoost MultiQuantile โมเดลเดียว 3.5%) ทุกแถวถูก sort ก่อนใช้ จึงไม่ใช่สาเหตุของคะแนน แต่เป็นอีกเหตุผลที่โมเดลแยกต่อ alpha หยาบกว่า
- **Runtime:** LightGBM 10 alphas ใช้ 81s ต่อ 3 fold เทียบ CatBoost MultiQuantile 107s ทั้ง run 197s
- **ข้อจำกัด:** LightGBM ใช้ค่า default ตามแผน ไม่ได้ tune (ตามกฎ time budget) LightGBM ที่ tune แล้วอาจปิดช่องว่างได้บ้าง แต่ช่องว่าง −0.0079 บนแถว spender ใหญ่กว่าที่การ tune ทั่วไปมักให้ (ยังไม่ได้พิสูจน์)
- **ทำต่อ:** oracle ยังบอกว่าขั้น "ใช้เท่าไร" มีที่ให้ปรับ แต่โมเดลตระกูลที่สองบน feature ชุดเดิมไม่เจอส่วนนั้น ทางที่น่าลองต่อจึงน่าจะเป็นข้อมูลใหม่สำหรับยอด (feature ของ amount model) มากกว่าการเพิ่ม learner (ข้อเสนอ ยังไม่ได้ทดสอบ)
