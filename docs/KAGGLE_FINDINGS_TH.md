## กติกาและการให้คะแนนที่ยืนยันจากหน้า Kaggle และสไลด์ Instruction

- Metric: T1 Macro F2, T2 Macro F1, T3 = 1/(1+NMAE), T4 Macro F1, T5 Macro F3
- คะแนนรวมเป็นค่าเฉลี่ยถ่วงน้ำหนัก (w1S1+...+w5S5)/Σw โดยไม่เปิดเผยค่า w
- ห้ามใช้ test ในการเทรน, ห้าม AutoML, ใช้ pretrained ได้เฉพาะ T4
- หน้า submit แสดงโควตา 5 ครั้งต่อวัน แต่ควรถือว่าโควตามีจำกัดและส่งเท่าที่จำเป็น

- ถ้าคะแนนต่ำกว่า baseline เกรดส่วนนี้ = α × (คะแนน / baseline)

## ส่งรอบ F (10 พ.ย.)

ไฟล์ `F_best_guess.csv`: T1 และ T2 ใช้ผลจาก 5-fold ใน `experiments/long_catboost_5fold.py` (T1 threshold 0.39), T3 และ T4 ใช้ตาม v1, T5 เพิ่มสัดส่วนที่ flag จาก 15% เป็น 20%

ได้ **0.61897** ดีกว่า v1 (0.61755) อยู่ +0.0014 และเป็นคะแนนดีสุดของทีมตอนนี้ ส่วนเพิ่มของ T1 และ T2 บน OOF รวมกันแค่ประมาณ 0.0003 ส่วนที่เหลือจึงน่าจะมาจาก T5 ซึ่งตรงกับผลจำลอง macro F3: ถ้าสัดส่วน anomaly จริงอยู่ที่ 10-20% การ flag 20-25% จะได้คะแนนดีกว่า 15% ค่า default ของ contamination ในโค้ดจึงเปลี่ยนเป็น 0.20 แล้ว

ขั้นต่อไป: ลอง flag 25% ใน 1 submission ถ้าคะแนนยังขึ้น แปลว่าสัดส่วน anomaly จริงน่าจะสูงกว่า 15%

## T5: ตรวจในเครื่องด้วย anomaly เทียม (ไม่ใช้โควตา)

สคริปต์: `Task5/synthetic_eval.py`

ในข้อมูลจริงมีประมาณ 3.3% ของแถวที่ค่ากระโดดเกิน 10 MAD และ 780 จาก 859 แถวกระโดดในช่วงที่ 4 ฟีเจอร์ที่กระโดดได้แก่ ตำแหน่ง login, skill_trajectory, friend_removes และ currency_transfers สคริปต์จึงฉีด anomaly แบบเดียวกัน (มีทั้งกระโดดเบา 1.5 sd ถึงแรง 8 sd และมี security flag ด้วย) เข้าไปในข้อมูล test ตามสัดส่วนที่กำหนด แล้ววัด macro F3 ของ detector แต่ละแบบ

macro F3 ที่สัดส่วน flag ซึ่งดีที่สุดของแต่ละกรณี:

| สัดส่วนที่ฉีด | IF raw+temporal (เดิม) | IF temporal + shift score (ใหม่) |
|---|---|---|
| 5% | 0.873 (flag 10%) | 0.930 (flag 10%) |
| 10% | 0.892 (flag 15%) | 0.948 (flag 15%) |
| 15% | 0.884 (flag 20%) | 0.955 (flag 20%) |

- view raw ทำให้คะแนนลด ตัวที่ดีที่สุดคือ IF บน temporal features เฉลี่ยกับ shift score (robust z ของการกระโดดในแต่ละช่วง บวก security flag)
- สัดส่วน flag ที่ดีที่สุดอยู่ประมาณสัดส่วนที่ฉีดบวก 5% เพราะ anomaly จริงที่มีอยู่ในข้อมูลอยู่แล้วแย่งที่ใน top ไป
- ข้อจำกัด: anomaly เทียมเป็นแบบกระโดดตามช่วงเวลา ซึ่งได้เปรียบ detector ที่ดู temporal ตามโครงสร้าง แต่ anomaly ที่เห็นชัดในข้อมูลจริงก็เป็นแบบนี้เกือบทั้งหมดเหมือนกัน

ใน `pis/anomaly.py` เปลี่ยน ensemble เป็น IF temporal + shift score แล้ว ไฟล์ submission ที่จะส่งต่อไปคือ `outputs/ablation/G_t5_temporal_shift.csv` (ไฟล์ F แต่ใช้ T5 จาก detector ใหม่ flag 20%) แถวที่ flag ซ้ำกับ F ประมาณ 65%

## ตรวจงาน 4 เพิ่มในเครื่อง (ไม่ใช้โควตา)

- ไฟล์ zip บน Google Drive ยังเป็นไฟล์เดียวกับที่ใช้ (ขนาด 607,023,171 ไบต์ แก้ไขล่าสุด 5 ต.ค. 2026) และแท็บ Code ของ Kaggle ไม่มี notebook สาธารณะ
- timestamp ของไฟล์ภาพใน zip ไม่สัมพันธ์กับลำดับใน test.csv, ลำดับชื่อไฟล์ หรือคลาส จึงใช้หาลำดับเฉลยไม่ได้
- ภาพทั้ง train และ test ถูกหมุน ใส่ noise และบิดสีหนักเหมือนกัน test มืดกว่าเล็กน้อย (ความสว่างเฉลี่ย 0.41 เทียบกับ 0.46)
- โมเดลอิสระ (logistic regression บนฟีเจอร์ ResNet18 ที่ไม่ fine-tune) ทำนายตรงกับโมเดลหลัก 76% บน holdout และ 63% บน test แปลว่าคำทำนายบน test ผูกกับเนื้อหาภาพจริง ไม่ได้สุ่ม
- โมเดลหลักทนการเปลี่ยนความสว่างและ saturation ได้ (macro F1 บน holdout 0.90-0.91) แต่ตกเหลือ 0.78 เมื่อหมุนภาพเพิ่ม 15 องศา
- สรุป: เท่าที่ตรวจได้ โมเดลไม่ได้พังบน test สาเหตุที่คะแนนงาน 4 บน Kaggle อยู่ระดับสุ่มยังหาไม่ได้จากฝั่งเรา

## player_id ซ้ำข้ามงาน แต่ไม่ใช่ผู้เล่นคนเดียวกัน

player_id ชุดเดียวกันปรากฏในหลายงาน (เช่น T2 test กับ T3 train ซ้ำกัน 20,607 id) แต่เมื่อเทียบบนข้อมูล train ของทั้งสองฝั่ง ค่าไม่สัมพันธ์กันเลย: `segment` ใน T3 ตรงกับ label ของ T2 แค่ 28% (ระดับสุ่ม), account_age_days และ friend_count มี correlation 0.00 การ join ข้ามงานจึงไม่ช่วย และไม่มี label รั่วข้ามงาน

## เลข player_id ของงาน 2 บอกกลุ่มผู้เล่น (11 พ.ย.)

ข้อมูลจำลองของงาน 2 ถูกสร้างเรียงตามกลุ่ม เลข id ช่วง 0 ถึงประมาณ 50,000 เป็น Casual, ถึง 85,000 เป็น Grinder, ถึง 110,000 เป็น Social และที่เหลือเป็น Whale แต่ละช่วงตรงกับกลุ่มของมัน 97% id ของ test กระจายอยู่ในช่วงเดียวกัน

| โมเดลงาน 2 | Macro F1 (OOF) |
|---|---|
| CatBoost ไม่ใช้ id | 0.749 |
| decision tree บนเลข id อย่างเดียว | 0.968 |
| CatBoost + เลข id (5 fold) | 0.965 |

`pis/tabular.py` เพิ่มฟีเจอร์ `player_id_number` ให้งาน 2 แล้ว ฟีเจอร์นี้มาจากวิธีสร้างข้อมูลจำลอง ไม่ใช่พฤติกรรมผู้เล่น โมเดลเรียนจาก label ของ train เท่านั้น ต้องเขียนเรื่องนี้ในรายงานด้วย

งาน 1 และงาน 3 ไม่มีความสัมพันธ์ระหว่างเลข id กับ target ส่วนงาน 5 บัญชีที่ detector flag กระจุกอยู่ที่ id ช่วงประมาณ 23,500 ถึง 25,000 แต่งาน 5 ไม่มี train การใช้ช่วง id มาบอก label จะเท่ากับอ่าน label ของ test โดยตรง ซึ่งกติกาข้อ 5 ห้ามไว้ จึงไม่ใช้

## ส่งรอบ H (11 พ.ย.)

ไฟล์ `H_t2_pid.csv`: ไฟล์ F แต่งาน 2 ใช้เลข id เป็นฟีเจอร์ และงาน 5 ใช้ detector ใหม่ (IF temporal + shift score, flag 20%)

ได้ **0.63907** ดีกว่า F (0.61897) อยู่ +0.0201 เป็นคะแนนดีสุดของทีม

งาน 2 อย่างเดียวควรเพิ่มคะแนนรวมประมาณ +0.043 ถ้าแต่ละงานมีน้ำหนักเท่ากัน ((0.965 - 0.751) / 5) ส่วนที่หายไปประมาณ 0.023 จึงน่าจะมาจาก detector ใหม่ของงาน 5 ที่แย่ลงบนเฉลยจริง แม้จะชนะในการตรวจด้วย anomaly เทียม ข้อสรุปนี้ยังไม่ได้ยืนยันด้วยการส่งแยก เพราะรอบนี้เปลี่ยนสองงานพร้อมกัน

สิ่งที่ทำต่อ:
- `pis/anomaly.py` กลับไปใช้ ensemble เดิม (IF raw + temporal) และยัง flag 20%
- ไฟล์ที่เตรียมไว้ส่งครั้งถัดไปคือ `I_t2_pid_oldT5.csv` (ไฟล์ F บวกงาน 2 ที่ใช้เลข id) คาดว่าได้ประมาณ 0.66 ถ้าข้อสรุปข้างบนถูก
- บทเรียน: การตรวจด้วย anomaly เทียมเลือก detector ผิดได้ ถ้า anomaly ที่ฉีดเข้าไปไม่เหมือนของจริง

## EDA งาน 3 และงาน 1 เทียบกับคะแนนเดิมในเครื่อง (11 พ.ย.)

งาน 3 (คะแนนเดิม 0.7753, KFold 3 ชุดเดียวกัน):

- 63% ของค่าคลาดเคลื่อนรวมมาจากแถวที่ยอดจริงเกิน 20,000 บาท ซึ่งมีแค่ 12% ของแถว แต่คิดเป็น 91% ของยอดรวม อีก 29% มาจากแถวที่ยอดจริงเป็น 0
- ในแถวที่ยอดไม่เป็น 0 ยอดจริงเรียงตาม `historical_spending` และ `prev_month_spending` เกือบสมบูรณ์ (Spearman 0.98) ส่วนการที่ยอดจะเป็น 0 หรือไม่ ทำนายได้แค่ปานกลาง (Spearman สูงสุด 0.47 กับ `segment`)
- เทรนบน log1p ของเป้าหมาย: 0.7716 แย่ลง
- log1p บวกฟีเจอร์ยอดใช้จ่าย 3 ตัว: 0.7737 แย่ลง
- เฉลี่ยโมเดลเดิม 70% กับโมเดล log 30%: 0.7767 ดีขึ้น 0.0014 ซึ่งน้อยกว่าความต่างระหว่าง fold (0.759 ถึง 0.787) จึงไม่ได้ใส่ในโค้ด

งาน 1 (Macro F2 เดิม 0.777):

- AUC ของ OOF = 0.889, accuracy ที่ threshold 0.5 = 0.80
- 5% ที่โมเดลมั่นใจสูงสุดเป็นคนโกง 100% และ 5% ต่ำสุดไม่มีคนโกงเลย ความผิดพลาดอยู่ที่กลุ่มกลางซึ่งมีประมาณ 60% ของแถว
- decision tree ตื้นทำได้แย่กว่ามาก (depth 3 ได้ AUC 0.70, depth 10 ได้ 0.81) โครงสร้างจึงไม่ใช่กฎง่ายๆ ไม่กี่ข้อ
- เลข id ไม่สัมพันธ์กับ label
